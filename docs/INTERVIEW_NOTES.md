# Index Advisor — Interview Notes

Questions likely to come up, how to answer them, and technical defenses for design choices someone might push back on. For build status see `CURRENT_PROGRESS.md`; for full design rationale see `ARCHITECTURE.md`.

## 30-second pitch

"An Index Advisor for PostgreSQL — takes a SQL query or a whole workload of queries, and instead of guessing which columns should be indexed, it actually generates candidate indexes, creates them for real, measures the before/after query plan and execution time with `EXPLAIN ANALYZE`, drops them again, and only recommends what it measured to actually help. At the workload level it goes further: it doesn't just recommend the best index per query, it picks a *set* of indexes that covers the whole workload without redundancy — a real greedy algorithm, not a list of per-query answers concatenated together. Java/Spring Boot backend, real PostgreSQL, HTTP API, no frontend yet."

## Architecture & Design Questions

**Q: Walk me through the architecture end to end.**
`POST /analyze` or `/analyze-workload` → `AdvisorController` → `QueryAdvisor`/`WorkloadQueryAdvisor` → `SqlParser` (SQL text → table + filter columns) → `CandidateGenerator` (columns → candidate indexes) → `IndexEvaluator` (creates each candidate for real, runs `EXPLAIN ANALYZE` before/after, drops it) → `RecommendationEngine`/`WorkloadRecommendationEngine` (filters, ranks, and — at workload scope — picks a non-redundant set) → JSON response. Every step is a separate, independently-testable class (see Design Principle in `ARCHITECTURE.md`).

**Q: Why Java over Python?**
Checked against an explicit rule: if Java materially limits the final product, switch to Python — it doesn't, for anything actually built. Reasons for Java: existing familiarity (real velocity), it fills a resume gap, and the project's core data model (a pipeline of well-defined objects — `ParsedQuery` → `CandidateIndex` → `EvaluationResult` → `Recommendation`) is a natural fit for Java's type system. The one real trade-off: Python has `pglast`, a direct binding to Postgres's actual parser (`libpg_query`); Java doesn't have an equivalent, so `JSqlParser` (ANTLR-based, not Postgres-exact) is used instead. Bounded risk — `EXPLAIN`'s own `Relation Name`/`Filter`/`Index Cond` fields are available as an authoritative cross-check if ever needed. The actual performance bottleneck in this project is PostgreSQL's own query planning, not the host language — Java's speed advantage over Python isn't really a factor here either way.

**Q: Why not use an ORM like Hibernate or Spring Data JPA?**
The entire tool exists to construct and inspect exact SQL text (`EXPLAIN ANALYZE ...`, `CREATE INDEX ...`) and read Postgres's raw JSON plan output. An ORM's whole purpose is to hide SQL from you — the opposite of what an index advisor needs. Raw JDBC keeps the SQL fully visible and controllable, and the boilerplate cost is small, contained entirely in one class (`PostgresManager`).

**Q: Why records instead of regular classes?**
Every pure data type in the project (`ParsedQuery`, `CandidateIndex`, `EvaluationResult`, `Recommendation`, etc.) is created once from a computation and never mutated — records give immutability, `equals`/`hashCode`, and `toString` for free, with no boilerplate. It's not just convenience: `CandidateGenerator.generateForWorkload()` deduplicates candidates via a `LinkedHashSet<CandidateIndex>`, which only works correctly because two candidates with the same table and columns are automatically `.equals()` — that's the record's generated structural equality doing real work, not incidental. Classes that *do* something (talk to a database, run an algorithm) stay ordinary classes.

**Q: What's the difference between `EvaluationResult` and `Recommendation` — why two types for what sounds like the same thing?**
`EvaluationResult` is a raw, honest measurement — includes negative and below-threshold results, e.g. `products(status)` at -6.8% improvement is a completely valid `EvaluationResult`. `Recommendation` is a *decision* — filtered, ranked, tiered, only what actually clears the bar. Keeping them separate means `RecommendationEngine` can change its filtering threshold or ranking logic without re-running any (slow, real) database experiments — the raw measurements already exist independently of what was decided from them.

**Q: Why is `WorkloadAdvisor` separate from `WorkloadQueryAdvisor`? Seems like it could be one class.**
`WorkloadAdvisor` only understands the workload (produces a `WorkloadProfile` — frequency counts, nothing else). `WorkloadQueryAdvisor` is the orchestrator that actually decides what to recommend, calling `WorkloadAdvisor`, then `CandidateGenerator`, then `WorkloadIndexEvaluator`, then `WorkloadRecommendationEngine`. This was a stated design principle from the very start of the project — Workload Advisor understands, Index Advisor recommends — and keeping them as separate classes keeps that boundary real in the code instead of just being an idea in a doc.

## Algorithms

**Q: How do you choose which indexes to recommend for a whole workload? Isn't that NP-hard?**
Yes, structurally. Choosing a set of indexes that jointly covers a workload well, where candidates overlap in what they can help, is the same shape as Set Cover / Knapsack — both NP-hard in general. I used a greedy heuristic: repeatedly pick the candidate with the best *marginal* contribution (summed improvement across queries not already well-served by an earlier pick), stop once nothing clears a threshold. This is a well-known, reasonable approximation for this problem class — not coincidentally close in spirit to real index-tuning research (Microsoft's AutoAdmin / Chaudhuri & Narasayya line of work uses similar marginal-utility reasoning, with considerably more machinery than mine). I explicitly considered an exact ILP/DP formulation and decided it was disproportionate engineering for a 9-candidate workload — noted as a future improvement, not something I didn't think about.

**Q: Walk me through the greedy algorithm with a concrete example.**
Workload had `products(category_id)` (applies to 3 queries: filters on `category_id=25`, `category_id=100`, and `category_id=25 AND status='active'`) and `products(category_id, status)` (applies to only the third query, since it's the only one filtering on both columns). First iteration: `products(category_id)`'s marginal score sums its improvement across all 3 queries (~275 combined), beating the composite's single-query score (~96). `products(category_id)` gets chosen; all 3 of its queries get marked "covered." Second iteration: the composite's only applicable query is now already covered, so its marginal score drops to 0 — it never gets chosen. Result: the workload-level advisor picks one index instead of two redundant ones. Proof this isn't a lucky guess: the *per-query* advisor (`QueryAdvisor`), looking at that third query in isolation, recommended both — the workload-level view caught a redundancy the per-query view structurally cannot see.

**Q: How do you decide which candidate indexes to even generate?**
Per query: one single-column candidate for each column in the WHERE clause, plus one composite covering all of them if there's more than one. Not the full power set of subsets/orderings — deliberate, to avoid combinatorial explosion once more filter columns (or JOINs) are involved. Across a workload, candidates from different queries are deduplicated.

**Q: What's `appliesTo()` and why doesn't it model Postgres's real leftmost-prefix rule?**
`appliesTo(query)` decides whether a candidate could plausibly help a given query — same table, and every one of the candidate's columns is actually filtered by that query. Postgres's real rule is more permissive (a composite index on `(a,b,c)` can also serve a query filtering on just `a`), but I don't need to model that because I already generate a dedicated single-column candidate for every filter column separately — the "just one column of what would be a composite" case is already covered by a different candidate. It's a deliberate simplification, not a gap I missed.

## Measurement & Correctness

**Q: How do you know a recommended index actually helps, rather than just assuming WHERE-clause columns should be indexed?**
That's the whole point of the design — nothing gets recommended without being measured. `IndexEvaluator` actually creates the candidate index, runs `EXPLAIN ANALYZE` (which really executes the query) before and after, and drops the index again. If the plan doesn't change and execution time doesn't improve, it's not recommended — verified concretely: `products(status)` consistently measures around -6.8% improvement (a real negative), and it gets filtered out at every level (single-query and workload).

**Q: Why actually `CREATE INDEX` instead of just asking the planner what it would cost?**
Planner cost estimates depend on table statistics being fresh and cost constants (`random_page_cost` etc.) matching real hardware — either can be wrong. Real, measured execution time is the ground truth I wanted the whole project built around. The trade-off is speed — real DDL doesn't scale to hundreds of candidates, which is exactly why `HypoPG` (Postgres's hypothetical-index extension) is the next planned step for screening at scale, reserving real DDL for validating the finalists. Not built yet, but the architecture (an `IndexEvaluator` with one `evaluate(candidate, query)` method) is already shaped so swapping the underlying mechanism later is a change inside one class, not a redesign.

**Q: Tell me about a bug you found and fixed.** *(two good stories — pick based on what they're probing for)*

*Parser bug (good for "how do you verify third-party library behavior"):* JSqlParser 5.x changed how it parses a parenthesized boolean group like `(status='a' OR status='b')` — in older versions it was a `Parenthesis` node with a single child; in 5.x it's a `ParenthesedExpressionList`, effectively a list. My first implementation only handled the old `Parenthesis` shape and silently dropped a column from the result — `[customer_id]` instead of `[customer_id, status]`, no error, just quietly wrong. I found the real cause by writing a small throwaway program that printed the actual class names in the parsed AST, rather than continuing to guess from memory of the API — and before that, I'd already made a habit of using `javap` against the actual downloaded jar to confirm method signatures before writing code against them, which is what let me catch this quickly once the symptom appeared. Fixed by handling `ExpressionList` generically and dropping the deprecated `Parenthesis` branch.

*Measurement bug (good for "how do you handle noisy/nondeterministic systems," "tell me about a subtle bug"):* During live HTTP testing, one `/analyze` response showed `products(status)` at ~40% improvement — but the "observed effect" field said `Seq Scan -> Seq Scan`, meaning the query plan hadn't actually changed. That's a contradiction: if Postgres kept the same strategy, there's no mechanism for a real 40% speedup. Root cause: `CREATE INDEX` requires a full table scan to build the index, which warms the OS/Postgres page cache regardless of whether the resulting index ever gets used — so the "after" measurement looked faster purely from that warm-up, not from the index doing anything. Fixed in two steps: first, took the median of 3 repeated measurements with a warm-up run on both the before and after side (symmetric protocol) — this reduced the artifact from ~40% to ~16.7%, but didn't eliminate it, because the `CREATE INDEX` scan happens *between* the two measurement blocks, so "after" still starts from a more cache-warm state than "before" ever did. Second fix: if the plan's node type didn't actually change, clamp the improvement to zero or below — there's no honest mechanism for a real improvement without a strategy change, so any remaining positive number is definitionally noise. Verified the fix by re-running the exact same scenario and confirming the number landed back at ~-5.6%, matching what I'd originally measured before the bug was ever introduced by earlier changes — and then re-ran the whole pipeline to confirm this wasn't just a cosmetic number fix, it actually restored correct set-selection behavior (the workload advisor had, for a window of time, been at risk of recommending a useless index due to this).

*Concurrency bug (good for "tell me about a race condition," "how does connection pooling change your assumptions"):* Right after adding HikariCP pooling, I fired 5 identical concurrent requests at `/analyze` as a sanity check — 4 came back `500`. The error was `CREATE INDEX "idx_experiment_orders_customer_id" ... relation already exists`. Root cause: the index name was built deterministically from just table+columns, so two concurrent requests evaluating the same candidate raced on `CREATE INDEX` — whichever request's transaction committed first "won," and every other one failed. This bug had existed since the very first version of the evaluator; it just was never observable before, because without pooling, each database call paid a full connection-establishment cost that happened to serialize requests enough to hide the race. Fixed by appending a monotonic counter to every generated index name, so concurrent evaluations of the same candidate never collide. Re-tested with the same 5 concurrent requests: all 5 succeeded.

*Correctness bug in a bug fix (good for "tell me about a mistake you caught yourself," shows real self-review, not just first-pass work):* The same-node-type clamp from the measurement bug above only compared the *root* node of the query plan. That's correct for single-table queries — the root is the whole story. But testing a join query (`customers JOIN orders ON c.id = o.customer_id WHERE c.id = 500`) that I already knew by hand should show a ~93% improvement, the automated result came back as "no recommendation." The root node was `Nested Loop` before and after — Postgres correctly kept the same *join strategy*, but the *nested* inner scan had changed from `Seq Scan` to `Bitmap Heap Scan`, exactly the improvement I expected. My own clamp, built to fix one bug, was silently causing a different one — and doing so for precisely the scenario (join-column indexing) the feature I'd just built existed to handle. Fixed by walking the entire plan tree depth-first and comparing the full sequence of node types, not just the root; for single-table plans this is provably identical to the old behavior (a leaf plan's node-type list is just one element), which I confirmed by re-running the full pre-existing test suite unchanged.

*Calibration bug in generated data (good for "tell me about a time you double-checked your own assumption," relevant to any "how do you validate synthetic/test data" question):* When adding realistic skew to customer/product activity (Zipfian sampling instead of uniform), my first exponent choices (1.1/1.2) were picked because they "sounded moderate," not because I'd checked the output. I queried the actual result before trusting it, and found one customer held 15% of all 10,000 orders, one product was in 17% of all order line items — a single monopolizing outlier, not the realistic long-tail skew I was going for. Recalibrated by treating it like any other measurement problem in this project: query the actual top-10%-share and max-single-item concentration, adjust the parameter, re-measure, repeat — landed on 0.5/0.6, verified independently on two separate database instances (local and Supabase) with two different random draws, both converging to matching concentration numbers (~29%/~38%). The lesson I'd give in an interview: synthetic test data deserves the same "measure it, don't assume it" discipline as production code — a formula that sounds reasonable can still produce an unusable dataset if you don't check.

**Q: Why does data distribution matter to index selection?**
Because selectivity determines whether PostgreSQL can avoid scanning most of the table. A predicate that matches 1% of rows and one that matches 60% of rows can produce completely different planner decisions for the identical SQL shape, and that's entirely a function of the underlying data's distribution, not the query text. I saw this directly in this project: `products.status` (3 values, ~66% weighted to one value) never earned an index recommendation, while `orders.status` (5 roughly-even values, ~20% each) did — same kind of column, same kind of query, opposite outcome, because of selectivity. It's also why I deliberately introduced real skew into the generated data (Zipfian customer/product activity, not uniform): a uniformly-distributed workload understates how much indexes matter in practice, because real access patterns concentrate on a minority of rows far more than uniform random data ever will.

**Q: How do you verify your code actually works, not just that it compiles?**
Two layers now. Every milestone was, and still is, verified against the real local Postgres database, not mocks — run the actual pipeline, read the actual output, and for the DDL-mutating parts, explicitly check `pg_indexes` afterward to confirm no experimental index was left behind; for the HTTP layer, that means literally starting the server and hitting it with `curl`, including sending a malicious payload to confirm a security fix actually rejects it. On top of that, there's now a 42-test JUnit suite (7 test classes) — pure unit tests for everything that doesn't need a database (parsing, candidate generation, the recommendation/ranking logic, the greedy set-selection algorithm using synthetic-but-realistic data), and one real integration test class for what does need a database, deliberately not mocked, matching the project's whole "measure the real thing" ethos. Both real bugs found this session (the concurrency race and the join plan-shape bug above) now have permanent regression tests, not just a one-time manual fix.

## Security

**Q: You're building `CREATE INDEX` statements with string concatenation — isn't that SQL injection?**
It was a real, live risk, and I fixed it, not just documented it. JDBC's `PreparedStatement` can only parameterize *values*, never *identifiers* like table/column/index names — there's no way to write `CREATE INDEX ? ON ?(?)` in any JDBC driver, so some form of string-building is unavoidable for DDL. The actual exploitable mechanism: PostgreSQL's JDBC driver executes `Statement.execute()` via the simple query protocol, which allows multiple `;`-separated statements in a single call — so a crafted "column name" like `category_id; DROP TABLE customers; --`, if it ever got extracted from attacker-controlled SQL text by the parser, could execute as a second statement. I closed it with two layers: a schema allowlist (loaded once from `information_schema`, so only table/column names that genuinely exist in the real database can ever reach a DDL string) and quoted identifiers as defense-in-depth. I tested this with the actual payload through a real HTTP request — got a 400 response, and confirmed via `psql` afterward that the target table was untouched.

**Q: How do you make sure your index experiments don't damage real/production data?**
Two layers. Architecturally, the project maintains two separate Postgres databases — a shared Supabase instance treated as read-only canonical data, and a local sandbox specifically for experiments — so real DDL never has a path to the shared data. But a separate database alone is just convention unless something enforces it, so `IndexEvaluator`'s constructor also runs a hard runtime check (`SELECT current_database()`) and throws immediately if it's not pointed at the sandbox database. That's a guarantee, not a policy — verified in practice across every milestone that no experimental index was ever created anywhere but the sandbox.

## Trade-offs & Limitations

**Q: What's the biggest limitation of your project right now?**
Two candidates, both honest, neither hidden. First: JOIN support only recognizes simple, single-condition equi-joins — a query with a multi-condition `ON` clause, a non-equality join, or a three-table chain won't get join-column candidates proposed for it; that's a stated scope boundary (I chose not to guess at shapes I couldn't verify, since a wrong guess proposes a misleading index recommendation, which is worse than proposing none), not something I didn't think about. Second: `HypoPG` is built, working, and cross-validated against real measurements, but it's not yet wired into the actual workload-level candidate-selection pipeline as the fast screen-then-validate two-phase process it's designed for — at the current candidate-count scale (roughly a dozen), real `CREATE INDEX` evaluation isn't actually the bottleneck yet, so I built and proved the mechanism rather than forcing a pipeline rewire to solve a problem I don't have yet.

**Q: What would you do differently, or what's next?**
In priority order: an automated test suite (everything so far has been verified by hand against a real database, which is rigorous but not regression-proof — a test suite would have caught the cache-warming bug in seconds instead of requiring me to notice a contradiction in printed output); `HypoPG` integration so evaluation can scale past a handful of candidates; JOIN support; and a real quantitative cost model (right now the "trade-off" side of a recommendation — storage, write overhead — is generic text, not measured numbers, even though the benefit side is measured precisely).

**Q: How would you rate this project, and why not higher?**
Strong technical substance — real DB internals, a genuine (if simple) NP-hard-adjacent algorithm, honest measurement discipline including catching and fixing my own bugs live. What caps it: no automated tests yet, no frontend yet (until Milestone 15 lands, it's an API a recruiter can't click through), and it's a solo, unvalidated project — no external users, no published results. That last point is a real ceiling on any solo project, not specific to this one: the highest tiers of "impressive" usually need someone else's validation, not just more code from me.

## Comparisons to real tools

**Q: How does this compare to something like pganalyze or dexter, or academic work on this problem?**
The core idea — measure real before/after impact rather than guessing from WHERE clauses — matches how serious tools approach it. Where this project is behind: production tools use Postgres's `HypoPG` extension for hypothetical indexes so they can screen many candidates without ever touching real storage; I currently create real indexes for every candidate, which doesn't scale (`HypoPG` integration is the planned next step, architected for but not yet built). On the algorithm side, the workload-level set-selection problem I'm solving with a greedy heuristic is the same problem space as Microsoft's AutoAdmin project (Chaudhuri & Narasayya) — their approach is considerably more sophisticated (proper cost-based search, storage constraints, "what-if" interfaces), but the underlying idea — pick indexes based on measured marginal benefit across a workload, not per-query — is the same, and I can speak to why greedy is a reasonable simplification (NP-hard problem, greedy is a standard approximation) rather than an oversight.
