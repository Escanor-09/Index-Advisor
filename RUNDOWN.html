The honest assessment

What's genuinely working, and what actually worries me about the path from here — not to talk the project down, but because planning against an inflated completion number produces bad timelines.

What's working

  • Every recommendation is proven, not asserted.IndexEvaluator actually runs CREATE INDEX, measures real EXPLAIN (ANALYZE, BUFFERS) execution time before and after with a warm-up + median-of-3 protocol, then drops the index again. Nothing gets recommended without being measured — a real negative case (products(status) at ~-6.8%) is filtered out at every level, not hidden.
  • A genuine two-codebase comparison, not a coin flip.Read a teammate's independent C++ backend (libpg_query, HypoPG-only, cpp-httplib) in full before deciding anything — found four real capabilities it had that this one didn't (ORDER BY awareness, existing-index awareness, prefix pruning, AI explanations), and two real defects (a likely thread-unsafe shared connection, hardcoded public credentials) along the way.
  • Five real bugs found and fixed this project, each with a full root-cause story.A JSqlParser parenthesized-group bug, a cache-warming measurement bug (~40% phantom improvement on an unchanged plan), a HikariCP index-name collision race under concurrent load, a join plan-shape clamp bug that silently zeroed a genuine ~93% improvement, and a Zipfian-skew calibration mistake caught by querying real output instead of trusting the formula.
  • A real algorithm, not heuristic hand-waving.Workload-level index selection is Set Cover/Knapsack-shaped (NP-hard); the greedy marginal-utility approach is explicitly positioned against the Microsoft AutoAdmin / Chaudhuri & Narasayya research lineage, with a concrete demonstrated case — 9 candidates down to 6, correctly dropping a composite made redundant once its shorter prefix was chosen first.
  • 94 tests, including real-database integration tests — zero mocking of the one thing that actually matters.Postgres behavior itself is never simulated; the integration test classes stand up real connections, create/drop real indexes, and assert against real pg_indexes state, cleaning up after themselves every time.
  • Security hardening that was actually tested with a crafted payload, not just reasoned about.A real SQL-injection vector in dynamically-built DDL (Postgres JDBC's simple-query-protocol multi-statement risk) was closed with a schema allowlist + quoted identifiers, then verified by sending an actual attack string through a live HTTP request and confirming via psql that the target table was untouched.
  • The frontend-backend connection is genuinely live, and a real integration gap was caught and fixed, not glossed over.Single-query analysis is verified end to end against the real local database through the real UI contract. When first "verified" via curl looked fine but the browser still couldn't talk to the backend, the actual cause (missing CORS config — curl doesn't enforce it, browsers do) was found and fixed, not waved away as "should be fine."
  • Data realism grounded in verified numbers, not assumed.Zipfian customer/product activity skew was recalibrated after directly querying the generated data and finding the first exponent choice produced a single monopolizing outlier — reproduced independently on two separate database instances (local and Supabase) with converging concentration numbers.
  • Existing capabilities were adopted honestly, with credit, not silently absorbed.ORDER BY-aware candidates, existing-index awareness, and prefix-domination pruning were ported natively from the teammate's proven C++ logic into this codebase — his code stays intact in the repo and git history; what carried forward was the value of the idea, not a copy-paste.
  • Storage cost is a real, measured number, not an estimate.pg_relation_size() is read while the experimental index still exists, threaded through EvaluationResult and Recommendation.tradeoffs as an actual byte count, not a guess.
  • The workload page — the project's strongest interview story — now has a real, demoable UI.Previously 100% mock data with no working spinner (a direct symptom of never making a real network call). Now fully wired to /analyze-workload with a real per-index cost/coverage aggregation layer, three ways to build a workload without touching a file dialog (preset dropdown, free-text, one-click quick-add chips), and a real loading state. Verified end to end against the live backend, not assumed from the code.
  • HypoPG is genuinely load-bearing now, and its actual value was measured honestly, not just claimed.New WorkloadHypoScreener screens every candidate before real DDL runs — a real architectural change, not a toggle. The benchmark (SCALABILITY_BENCHMARK.md) shows a modest, real, workload-dependent ~1.2x average speedup, including one case that's 10% slower — reported as measured, not rounded up. Root cause understood: at this project's 10,000-row tables, real CREATE INDEX is already cheap, so there's less cost for screening to avoid.
  • A real correctness bug in plan-change reporting, found and fixed with a verified before/after.Recommendation.observedEffect used to show only the plan's root node, which for a join can stay identical while the real change happens in a nested scan — exactly the scenario that produced a misleading "Nested Loop -> Nested Loop" line for a genuine 97%+ improvement. New QueryPlan.describeChange() fixes it, re-verified live on that exact query, not just in a unit test.
  • The public API now has real, verified size limits, not just assumed safety.An oversized 201-query workload is rejected in 9 milliseconds — measured live against the running server, proving the rejection happens before any real database work starts, not after a long wait.
  • The system is genuinely live, and a real deployment bug was found and fixed, not hand-waved.Backend on Render, frontend on Vercel — Docker first (multi-stage builds for both, database intentionally left uncontainerized since it's already Supabase-hosted), then a real bug: Render's dynamic $PORT binding wasn't wired to Spring Boot's server.port, so the service built clean but never went healthy. Fixed and re-verified live: a real /analyze POST against the live URL returned a genuine measured recommendation, a CORS preflight from the actual Vercel origin came back correct, and the deployed frontend's built JS bundle was fetched and grepped directly to confirm it calls the live backend, not localhost.
  • A merge from a teammate's branch was verified by running the real suite, not by reading the diff — and it wasn't clean.The merged commits renamed the sandbox database's expected name (index_advisor → ecom_test) inside the safety checks, but not in application.properties, the CLI entry points, four integration tests' hardcoded JDBC URLs, or the actual local database — 94 tests dropped to 1 failure + 6 errors, all the same IllegalStateException. Fixed (local DB renamed, all references synced) and back to 94/94. A second gap from the same merge — the frontend now requires VITE_API_URL with no local .env.local to supply it — was found and fixed the same way, before it could quietly break local dev for anyone pulling the branch.

What concerns me

  • CI now regenerates data fresh instead of restoring a fixed snapshot — a small, accepted trade-off.No committed multi-MB data dump means every CI run builds its own random 10,000-row dataset via the real populate scripts. Category assignment is dense enough (near 1:1 categories-to-products, verified while testing this) that the specific assertions in this suite are very unlikely to flip on an unlucky draw, but it's not literally zero risk the way testing against one fixed local database is.
  • Render's free tier has a real, disclosed cold-start cost.The backend spins down after inactivity; the first request afterward can take 50+ seconds, visible directly in Render's own dashboard warning. Not hidden from anyone demoing this live.
  • JOIN and WHERE-clause understanding is narrower than it sounds.Only single-condition equi-joins are recognized — no multi-condition ON clauses, no non-equality joins, no 3+ table chains, and no GROUP BY/HAVING/subquery/CTE awareness at all. A stated scope boundary, but a real one.
  • The public API bounds request *size*, not request *duration*.A compliant-sized workload (up to 200 queries, 150 candidates) can still legitimately take real minutes — see SCALABILITY_BENCHMARK.md. No wall-clock timeout or async cancellation exists yet; a slow-but-legal request still ties up a connection for its full duration.
  • Write overhead is now measured, but the number isn't clean enough to wire into Recommendation.tradeoffs yet.A dedicated benchmark (WriteOverheadBenchmark) found real per-statement INSERT/UPDATE/DELETE cost sits inside the noise floor of client-side timing at this project's current 10,000-row scale — individual trials ranged -40% to +44% with no consistent sign. Honest, not evasive: the write-side line still can't be a precise live number without a bulk-throughput or larger-scale measurement first (see the two new roadmap items below).
  • Still fundamentally a two-person project with zero outside validation.No external users, no code review from anyone besides the two contributors, no production traffic, no published results. That's a real ceiling on the rating regardless of how complete the roadmap gets.
  • A real credential leak is still live and public as of this writing.The teammate's C++ backend has Supabase database credentials hardcoded directly in source, pushed to a public GitHub repo — flagged clearly, not yet rotated.
  • No logging framework, and two config paths that still don't agree.Application code uses System.out.println throughout; Main.java's CLI path reads raw env vars independently of application.properties, unreconciled since Milestone 14.
  • Every measurement is single-machine, single point in time.Numbers are reproducible in shape, not exact figures — there's been no sustained concurrent-load testing beyond the specific 5-request race that exposed the HikariCP naming bug.

F · Workload advisor — index-set selection 12 pts10.0 earned
Why the exact optimizer is grayed out

An exact ILP/DP formulation for index-SET selection was explicitly considered and declined as disproportionate engineering for a roadmap that currently exercises single-digit-to-low-teens candidate counts. Greedy marginal-utility selection is a well-known, defensible approximation for this NP-hard problem class — the same spirit AutoAdmin-style research uses, with far less machinery. Revisit only if the candidate count grows enough that greedy's known failure modes actually start to bite.

Recommended sequencing

Ordered so there's a working, demoable improvement at the end of every step — never a stretch where the app is strictly worse than it is today.

  1. Wire the workload page to /analyze-workload — done

    Delivered wider than originally scoped: real per-index cost/coverage aggregation, three query-building modes (preset/free-text/quick-add) instead of a mandatory file upload, and the loading spinner that motivated the round in the first place. Verified end to end against the live backend.

  2. Docker Compose, brought up end to end — done

    Backend + frontend as one docker compose up (database excluded — already Supabase-hosted). Verified by actually building and running both containers, not just writing the Dockerfiles.

  3. Live deployment — done

    Backend on Render, frontend on Vercel — a real, public URL, the single biggest lever on the "rating" axis specifically. A real bug found and fixed along the way (Render's dynamic $PORT wasn't wired to server.port), then verified end to end: a live /analyze call, a CORS preflight from the real deployed origin, and the deployed JS bundle itself inspected to confirm it calls the live backend, not localhost.

  4. CI pipeline — done

    GitHub Actions runs the real 94-test suite (against a real Postgres + HypoPG, built fresh from a checked-in Dockerfile) and the frontend build on every push/PR. Verified locally end to end before being written, not written blind. Gates both hosts' existing auto-deploy for the first time.

  5. Rotate the leaked Supabase credentials

    Not code work, but genuinely urgent and currently outstanding — the teammate's C++ backend still has live database credentials hardcoded in a public repo.

  6. Wire HypoPG into the actual workload selection pipeline — done

    Screen cheaply with HypoPG, validate only promoted candidates with real DDL — and honestly benchmarked, not just shipped: a real but modest ~1.2x average speedup, understood to correlate with promotion ratio rather than workload size (see SCALABILITY_BENCHMARK.md).

  7. Storage/count budget for index-set selection — done

    New IndexSetBudget — a real second stopping condition in the greedy loop, not just measured-and-reported data going unused.

  8. Fix nested-plan observedEffect reporting — done

    Re-verified live on the exact query that originally exposed the bug — "Nested Loop -> Nested Loop" became an accurate description of the actual nested change.

  9. Harden the public API against expensive workloads — done

    Request-size limits (query count, candidate count, SQL length) rejected with a clean 400 in single-digit milliseconds. Deliberately doesn't cover wall-clock timeouts on a compliant-sized request or rate-limiting — flagged as separate future work, not silently folded in.

  10. Multi-condition JOIN support, then GROUP BY/HAVING awareness

    Natural extensions of already-shipped JOIN and ORDER BY support, in roughly that order of proximity to what already exists.

  11. Real write-path cost measurement — done, honestly inconclusive

    A dedicated benchmark found the real number is inside the noise floor of client-side timing at this project's current 10,000-row scale (two real measurement biases found and fixed along the way, same class of bug as the read-side cache-warming fix). Not wired into live Recommendation.tradeoffs yet — the number isn't clean enough to show a user. See the next item, which this directly motivates.

  12. Proper scalability experiment — more rows, not just 10,000

    Newly added. Both the write-overhead benchmark and the HypoPG screening benchmark independently hit the same wall: at 10,000 rows, real per-operation costs (index maintenance, real DDL) are small enough to sit near measurement noise. A real experiment across row counts (100K, 1M+) would show how read/write costs and the value of screening actually scale, not just confirm they're small at the one size this project has ever tested.

  13. Real-world dataset validation

    Newly added. Every result in this project, without exception, comes from generated data — realistic in shape (Zipfian skew, verified concentration numbers) but still synthetic. Running the same advisor against a real public dataset would test whether its recommendations and measured improvements hold up outside data this project's own generation code produced.

  14. Wall-clock timeouts and rate-limiting on the public API

    The size limits added this round bound how big a request can be, not how long a compliant one is allowed to run — a real, disclosed gap, not an oversight.

The pattern worth naming honestly: Group K is now the first group in the entire roadmap to hit 100%, and no layer anywhere sits below 70%. This round's two moves were both off-roadmap by design and both infrastructure, not new engine capability: a real CI pipeline (verified by actually building and restoring against Docker locally before writing the workflow, not written blind), and a write-overhead benchmark that came back honestly inconclusive rather than being massaged into a clean number it doesn't have yet. That second result is the more interesting one — it's the same "measure, don't assume" discipline this project has applied to every real bug found so far, just applied to a case where the honest answer is "the effect is real but too small to see with this method," not a satisfying percentage. The two items it motivated — a proper scale experiment and real-world dataset validation — are the newest additions to the roadmap, and the most natural next test of whether this project's numbers hold up past its own generated data.
